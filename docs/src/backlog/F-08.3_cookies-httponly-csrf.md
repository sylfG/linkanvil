**Descripción:**
Como Usuario de la web
Quiero **que mi token de sesión viaje en una cookie httpOnly y los endpoints state-changing requieran un token CSRF en cabecera**
Para que un XSS no pueda robar el JWT (cookie no accesible a JS) y un atacante remoto no pueda disparar acciones desde otro origen autenticadas con mis cookies.

**Criterios de Aceptación (Checklist):**

- [ ] **Happy Path:**
  **Dado que** el usuario hace `POST /auth/login`,
  **Cuando** recibe la respuesta,
  **Entonces** el navegador almacena `cerebro_session` (httpOnly, secure cuando aplica, samesite=lax) y `cerebro_csrf` (legible por JS); las llamadas siguientes incluyen automáticamente la cookie de sesión y el frontend echa el CSRF en `X-CSRF-Token`.

- [ ] **Edge Case:**
  **Dado que** un atacante intenta `POST /chats` desde otro origen con la cookie del usuario,
  **Cuando** llega al backend,
  **Entonces** `verify_csrf` rechaza con 403 porque `cerebro_csrf` (cookie) y `X-CSRF-Token` (header) no coinciden o falta uno.

- [ ] **Requisito Técnico:**
  `get_current_user` lee primero la cookie y, si no existe, cae al header `Authorization: Bearer` (compatibilidad con bots de Telegram y scripts). `verify_csrf` solo se aplica cuando la petición es cookie-authenticated, no para Bearer. Endpoints state-changing protegidos: `/profile/telegram`, `/ingest`, `/chat`, `/chats` (POST/DELETE), `/chats/{id}/messages`, `/admin/cf-cookies`. `JWT_SECRET_FILE` permite cargar el secret desde Docker secrets. Frontend: `credentials: "include"` en `fetch`, helper que lee `cerebro_csrf` de `document.cookie`.
