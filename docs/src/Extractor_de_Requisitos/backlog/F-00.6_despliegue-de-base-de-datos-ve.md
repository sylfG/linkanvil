**Criterios de Aceptación (Checklist):**

- [x] **Happy Path — Qdrant v1.17.1 con config bind-mounted:**
  **Dado que** el servicio `qdrant` declara `image: qdrant/qdrant:v1.17.1`,
  **Cuando** `docker compose up qdrant`,
  **Entonces** arranca con:
  - HTTP API en `:6333`, gRPC en `:6334`.
  - Config bind-mount: `./infra/qdrant/config.yaml:/qdrant/config/production.yaml:ro`.
  - Volumen persistente `qdrant-data:/qdrant/storage`.
  - Healthcheck TCP probe a 6333 (la imagen no trae curl/wget): `bash -c '</dev/tcp/localhost/6333'`.
  - Límite `2G/2cpu`.
  (verificado en `docker-compose.yml:463-497`).

- [x] **Dos colecciones declaradas en runtime:**
  **Dado que** el `embedder-worker` arranca y usa endpoints `/collections/cerebro_chunks/points` y `/collections/cerebro_recursos/points`,
  **Cuando** procesa el primer recurso,
  **Entonces** opera contra dos colecciones con propósitos distintos:

  | Colección | Granularidad | Uso |
  |---|---|---|
  | `cerebro_recursos` | 1 punto por recurso (vector representativo) | Búsqueda de colisionadores semánticos (similitud > 0.92 → F-03.3). |
  | `cerebro_chunks` | 1 punto por chunk de ~600 tokens (overlap 150 chars) | RAG en el endpoint `/chat` (top-k filtrado por tenant). |

  (verificado en `src/data/embedder_worker.py:165` upsert chunks, `:218` upsert recurso, `:303-340` search con `score_threshold: 0.92` contra `cerebro_recursos`).

- [x] **Aislamiento multi-tenant por filtro de payload (no por colección):**
  **Dado que** las dos colecciones son **compartidas entre todos los tenants**,
  **Cuando** un worker hace upsert,
  **Entonces** incluye `tenant_id` en el payload del punto (verificado `src/data/embedder_worker.py:156,206`).
  **Cuando** se hace una búsqueda,
  **Entonces** se aplica un filtro `{"key": "tenant_id", "match": {"value": tenant_id}}` (verificado `src/data/embedder_worker.py:298-310`). Esto evita el coste de crear/borrar colecciones por tenant y aprovecha el índice payload de Qdrant.

- [x] **IDs de punto deterministas (UUID v5):**
  **Dado que** un mismo recurso puede re-embebese tras un cambio de modelo,
  **Cuando** el worker calcula el ID del punto,
  **Entonces** usa `uuid.uuid5(_QDRANT_POINT_NS, f"{recurso_id}:{tenant_id}")` para el recurso y `f"{recurso_id}:{tenant_id}:chunk:{idx}"` para chunks (verificado `src/data/embedder_worker.py:34-39`). Esto garantiza idempotencia: re-procesar sobrescribe los mismos puntos.

- [x] **Similitud coseno con threshold 0.92 para colisiones:**
  **Dado que** el embedder calcula vectores normalizados,
  **Cuando** busca colisionadores con `POST /collections/cerebro_recursos/points/search`,
  **Entonces** usa `score_threshold: 0.92` y filtro por `tenant_id`; los matches alimentan el grafo semántico (`grafo_relaciones`) con tipos `ES_UN`/`CONTRADICE`/`EXTIENDE`/`VUELVE_OBSOLETO`/`ASOCIACION_GENERAL` clasificados por LLM (verificado `src/data/embedder_worker.py:255-340`).

- [x] **Requisito Técnico:**
  - **Patrón Dual respetado**: Qdrant **no** almacena texto crudo grande, solo vectores + payload mínimo (`tenant_id`, ID de referencia a Postgres, metadatos imprescindibles).
  - **Persistencia**: volumen nombrado `qdrant-data` (recreable solo si Postgres existe, ya que los recursos se re-embeben desde la fuente).
  - **Backup**: snapshots vía HTTP API (`POST /collections/<col>/snapshots`) — ver F-00.13.
  - **Routing Traefik**: `qdrant.localhost` mapeado al puerto 6333 (HTTP).
  - **Sin schema fijo en payload**: Qdrant es schemaless; los campos se añaden ad-hoc desde los workers.

**Decisiones tomadas tras el backlog original** (drift documentado):
- **Una colección por tenant fue descartada**: el aislamiento usa filtro de payload `tenant_id` en lugar de namespacing por colección. Razón: evita el coste de declaración por tenant y aprovecha el índice payload nativo de Qdrant.
- **Dos colecciones (no una)**: separar `cerebro_recursos` (búsqueda de colisiones, 1 vector representativo) y `cerebro_chunks` (RAG, granularidad fina) optimiza ambos casos sin tener que hacer doble cómputo en cada query.
- **UUID v5 deterministas**: permiten re-embedding idempotente — re-procesar un recurso sobrescribe el mismo punto sin acumular duplicados.
- **Healthcheck por TCP** (no HTTP): la imagen oficial de Qdrant no incluye curl/wget; un probe de socket `</dev/tcp/localhost/6333` es suficiente.
