**Descripción:**
Como Operador de la plataforma
Quiero **un runner de migraciones SQL idempotente y registrado en una tabla `cerebro.schema_migrations`**
Para que los cambios de esquema en producción no dependan de borrar el volumen (cosa que `init.sql` requiere para correr) y para que cada deploy aplique solo las migraciones nuevas, en orden y dentro de su propia transacción.

**Criterios de Aceptación (Checklist):**

- [ ] **Happy Path:**
  **Dado que** existe un nuevo archivo `0042_short_description.sql` en `infra/postgres/migrations/`,
  **Cuando** se ejecuta `bash scripts/migrate.sh`,
  **Entonces** la migración corre dentro de una transacción (`psql -1`), se inserta su versión en `cerebro.schema_migrations(version, applied_at)` y la siguiente ejecución reporta "schema is up to date".

- [ ] **Edge Case:**
  **Dado que** una migración falla a mitad,
  **Cuando** psql aborta,
  **Entonces** la transacción se hace rollback completo, el runner sale con código no-cero (CI falla) y la versión no se inserta en la tabla de bookkeeping.

- [ ] **Requisito Técnico:**
  Filenames con prefijo numérico (`NNNN_`); el runner extrae la versión con `(( 10#${BASH_REMATCH[1]} ))` para evitar interpretación octal. README documenta el wiring como contenedor one-shot `cerebro-migrate` con `condition: service_completed_successfully` antes de `cerebro-api`. Migración baseline `0001_baseline.sql` espeja `init.sql` para que las instalaciones existentes queden registradas en la versión 1 sin cambios destructivos.
