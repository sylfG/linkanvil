**Descripción:**
Como Plataforma Multi-Tenant,
Quiero **aislar cada tenant mediante PostgreSQL Row Level Security FORZADA en las tablas con datos por usuario**
Para que un fallo en lógica de aplicación nunca pueda exponer datos de otro tenant — el motor SQL es la última línea de defensa.

**Criterios de Aceptación (Checklist):**

- [x] **Happy Path (RLS habilitada y FORZADA):**
  **Dado que** PostgreSQL arranca con la migración `0001_baseline.sql`,
  **Cuando** se aplica la migración,
  **Entonces** las tablas `usuario_recursos`, `sesiones_chat`, `mensajes_chat`, `grafo_relaciones`, `outbox_eventos` tienen `ENABLE ROW LEVEL SECURITY` + `FORCE ROW LEVEL SECURITY` (`infra/postgres/migrations/0001_baseline.sql:140-185`) con policy `tenant_isolation` que filtra `USING (tenant_id = current_setting('app.tenant_id', true))` y `WITH CHECK` del mismo predicado.

- [x] **Inyección de `app.tenant_id` por sesión:**
  **Dado que** la API recibe un request autenticado,
  **Cuando** el handler obtiene una connection del pool,
  **Entonces** ejecuta `SELECT set_config('app.tenant_id', $1, true)` con el tenant del usuario **antes** de cualquier query (`src/api/database.py:122-124,327-330`); el flag `true` hace el setting LOCAL a la transacción para que no se filtre entre sesiones del pool.

- [x] **Edge Case (worker interno que necesita cross-tenant):**
  **Dado que** un worker (embedder, outbox_publisher, audit_cron) necesita leer/escribir múltiples tenants,
  **Cuando** se conecta al role `cerebro_service`,
  **Entonces** la sesión bypassa RLS porque el role se creó con `BYPASSRLS` (`infra/postgres/migrations/0001_baseline.sql:172-178` — `CREATE ROLE cerebro_service NOLOGIN BYPASSRLS`); ningún endpoint público corre bajo este role.

- [x] **Edge Case (tabla global sin RLS):**
  **Dado que** las tablas `recursos` (catálogo global de URLs deduplicadas) y `usuarios` (auth) son por diseño globales,
  **Cuando** se consultan,
  **Entonces** NO tienen RLS habilitada — el aislamiento per-tenant ocurre vía la tabla pivote `usuario_recursos` (que sí tiene RLS) y la lógica de auth a nivel API.

- [x] **Requisito Técnico:**
  - RLS habilitada **y** forzada (`FORCE ROW LEVEL SECURITY`) — sin `FORCE`, el owner de la tabla bypassa la policy.
  - Policy `tenant_isolation` usa el patrón `current_setting('app.tenant_id', true)` con flag `missing_ok=true` para devolver `NULL` (en vez de error) si el setting no se inyectó — la query simplemente devuelve 0 filas, no rompe.
  - Connection pool: cada checkout debe ejecutar `set_config(..., true)` antes de queries; el `true` final asegura scope LOCAL a la transacción.
  - Tablas globales (`recursos`, `usuarios`) documentadas explícitamente como sin RLS.

**Decisiones tomadas tras el backlog original** (drift documentado):
- Role dedicado `cerebro_service NOLOGIN BYPASSRLS` para workers internos: evita tener que setear `app.tenant_id` en cada query del embedder/outbox publisher, que necesitan ver múltiples tenants para hacer su trabajo.
- `set_config(..., true)` con scope LOCAL: crítico para que el pool de conexiones no filtre el setting entre requests.
- `recursos` y `usuarios` sin RLS por diseño (no es bug). La dedup global de URLs requiere catálogo compartido; la auth requiere lookup por email/credenciales sin tenant.
