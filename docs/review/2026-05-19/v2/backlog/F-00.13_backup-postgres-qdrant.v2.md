**Descripción:**
Como Operador de la plataforma
Quiero **un script `scripts/backup.sh` que produzca dumps gzipped de Postgres y snapshots de cada colección de Qdrant**
Para que un fallo de disco o una corrupción no signifique perder la KB del usuario (los únicos datos no recreables del sistema).

**Criterios de Aceptación (Checklist):**

- [x] **Happy Path — script idempotente, cron-friendly:**
  **Dado que** la cron del host invoca `bash scripts/backup.sh` (por ejemplo a las 03:00),
  **Cuando** el script termina exitosamente,
  **Entonces** existen en `BACKUP_DIR` (default `./backups`):
  - `postgres_<POSTGRES_DB>_<TIMESTAMP>.sql.gz` (output de `pg_dump --no-owner --clean --if-exists` gzipped a nivel 9).
  - `qdrant_<TIMESTAMP>.tar.gz` (tarball que contiene un `.snapshot` por cada colección descubierta vía `GET /collections`).
  Ambos con tamaño > 0 (verificado mediante `du -h` y log).
  `TIMESTAMP` usa formato ISO compacto UTC `YYYYMMDDTHHMMSSZ` (`date +%Y%m%dT%H%M%SZ`) — verificado en `scripts/backup.sh:18`.
  El script corre con `set -euo pipefail` y sin prompts interactivos (verificado en `scripts/backup.sh:11`).

- [x] **Edge Case — limpieza del snapshot dentro de Qdrant (sin residuos):**
  **Dado que** Qdrant crea cada snapshot como fichero dentro de su volumen (`/qdrant/storage/snapshots/`),
  **Cuando** el script ya ha descargado el `.snapshot` al host,
  **Entonces** invoca `DELETE /collections/<col>/snapshots/<snap_name>` para liberar espacio dentro del contenedor:

  ```bash
  curl -fs -X DELETE "http://localhost:6333/collections/$col/snapshots/$SNAP_NAME" >/dev/null || true
  ```

  (verificado en `scripts/backup.sh:57`). El `|| true` evita romper el script si el DELETE falla — el objetivo es no acumular snapshots, no garantizar atomicidad.

- [x] **Edge Case — retención y poda con `find -mtime`:**
  **Dado que** `BACKUP_RETENTION_DAYS` (default 7) define la ventana,
  **Cuando** el script entra en la fase final de retención,
  **Entonces** ejecuta:

  ```bash
  find "$BACKUP_DIR" -maxdepth 1 -type f \
      \( -name 'postgres_*.sql.gz' -o -name 'qdrant_*.tar.gz' \) \
      -mtime +"$RETENTION_DAYS" -print -delete || true
  ```

  (verificado en `scripts/backup.sh:65-68`). Solo borra ficheros mayores a `RETENTION_DAYS` días, dentro de `BACKUP_DIR` y restringido a los dos patrones de naming.

- [x] **Failure mode — exit no-cero ante cualquier fallo:**
  **Dado que** `set -euo pipefail` está activo,
  **Cuando** falla cualquier comando (pg_dump no conecta, curl recibe 4xx/5xx por `-f`, gzip falla),
  **Entonces** el script termina con código ≠ 0 para que la cron registre el fallo en su log — diagnóstico desde `journalctl -u cron` o el `MAILTO` de cron.
  Excepción intencional: el `DELETE` de snapshot interno usa `|| true` (best-effort cleanup) y el `find -delete` también (no debe romper la cadena si no hay ficheros que purgar).

- [x] **Requisito Técnico:**
  - **Variables de entorno**:
    - `BACKUP_DIR` (default `$SCRIPT_DIR/backups`).
    - `BACKUP_RETENTION_DAYS` (default `7`).
    - `POSTGRES_USER` (default `cerebro`), `POSTGRES_DB` (default `cerebro_brain`).
    - `POSTGRES_PASSWORD` se lee desde `.env` (sourceado con `[[ -f .env ]] && source .env`).
  - **Sin prompts**: usa `docker exec -e PGPASSWORD=…` para pg_dump dentro del contenedor `cerebro-postgres`.
  - **Off-host rsync**: los `.sql.gz` y `.tar.gz` son ficheros planos rsync-ables a una ubicación remota (paso adicional opcional, no incluido en el script).
  - **Descubrimiento dinámico de colecciones**: lee `GET /collections` con Python inline parser, así el script no requiere actualizarse cuando se añade una colección nueva.

**Decisiones tomadas tras el backlog original** (drift documentado):
- El TIMESTAMP usa formato ISO UTC `%Y%m%dT%H%M%SZ` (ej. `20260519T030000Z`) — facilita ordenación lexicográfica.
- `pg_dump --no-owner --clean --if-exists`: el dump puede restaurarse sobre cualquier cluster Postgres compatible, sin reproducir owners ni roles.
- gzip a nivel 9 (`gzip -9`) para máximo ratio de compresión (los dumps son altamente comprimibles por la repetición de tipos/columnas).
- La poda usa `-maxdepth 1` para no descender accidentalmente en subdirectorios — si el operador monta `BACKUP_DIR` sobre un volumen con otros archivos, no los toca.

**Pendiente operacional (no en el script)**:
- Cron del host. Ejemplo:
  ```cron
  0 3 * * * cd /opt/linkanvil && BACKUP_DIR=/mnt/backups bash scripts/backup.sh >> /var/log/linkanvil-backup.log 2>&1
  ```
- Rsync off-host del `BACKUP_DIR` a almacenamiento remoto (S3, NAS, etc.). El script intencionalmente no lo hace para mantener responsabilidad única.
