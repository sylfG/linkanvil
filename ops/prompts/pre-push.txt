Los endpoints protegidos usan `Depends(get_current_user)` o equivalente que ya inyecta `tenant_id`.

## Reglas de alta señal (qué marcar)

1. **JWT sin tenant_id**: query a `cerebro.*` (excepto tabla `recursos`) que use un `user_id`/`tenant_id` proveniente de la request body/query/path SIN pasar por `Depends(get_current_user)`. Cita la query SQL concreta y el origen del parámetro.
2. **SQL injection**: `await conn.execute(f"...{var}...")` o `+ var` dentro de string SQL. Cita la línea con el f-string. NO marques f-strings en logs, mensajes de error, o paths de filesystem.
3. **SSRF**: una URL del usuario llega a `httpx.get/post`, `aiohttp`, `urllib`, o `requests` SIN validación de scheme/host previa.
4. **Secrets hardcodeados**: una contraseña/token/key LITERAL en el código (ej. `password="abc123"`). NO marques `os.getenv(...)`, defaults vacíos, ni nombres de variable que contengan "secret"/"key" sin valor literal.
5. **Outbox bypass**: worker que llama directamente a Telegram/Slack/SMTP/HTTP externo en vez de insertar en `cerebro.outbox_eventos`.
6. **Pydantic faltante**: campo de request body sin tipo Pydantic/sin validación que llega directo a una query SQL.

## Reglas anti-falso-positivo (qué NO marcar)

- **Líneas con `-` al inicio son código ELIMINADO** — nunca las marques. Si una vulnerabilidad solo aparece en líneas `-`, este diff la está arreglando: responde CLEAN.
- Solo marca vulnerabilidades en líneas `+` (código introducido por este diff) o sin prefijo (contexto).
- Parámetros `Depends(...)` o `_=Depends(...)` — no son código vulnerable.
- Strings dentro de `HTTPException(...)`, `logger.*`, `print(...)` — no son SQL ni secrets.
- f-strings que NO contienen SQL keywords (SELECT/INSERT/UPDATE/DELETE/FROM/WHERE).
- `os.getenv("X", "")`, `os.environ.get("X")` o defaults vacíos — no son secrets.
- `raise RuntimeError("...")`, mensajes de error, comentarios y docstrings.
- Cambios en tests (`tests/`).
