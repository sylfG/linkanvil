**Descripción:**
Como Actor
Quiero **Clasificación inteligente de contenido y estimación lógica de la fecha útil (Volatilidad) para futuro**
Para que la funcionalidad orientada a eventos opere.

**Criterios de Aceptación (Checklist):**

- [x] **Happy Path (clasificación multi-dimensional):**
  **Dado que** llega texto limpio + título + URL a `_extract_metadata_with_llm`,
  **Cuando** el modelo `cerebro-lite` responde con el JSON estructurado del prompt,
  **Entonces** el sistema captura simultáneamente:
    - `category`: una de `{technology, science, business, health, politics, entertainment, education, other}`.
    - `volatility_score`: nivel de cambio esperado en `{baja, media, alta, dinamica}` (4 niveles: docs/tutoriales → noticias → precios).
    - `estimated_useful_life_days`: entero entre 30 y 365.
    - `expiration_date`: ISO `YYYY-MM-DD` si el texto menciona una fecha concreta de fin (deadline/caducidad), `null` si no aplica.
    - `event_date`: ISO `YYYY-MM-DD` del evento principal — el prompt instruye **usar el patrón `YYYY/MM/DD` en el path de URL** (típico prensa: `/2024/03/18/`) como pista cuando el texto no la indica explícitamente.
    - `temporal_class`: clasificación semántica `{evento, referencia, evergreen}`.
    - `valor_archivistico`: relevancia para archivo `{alto, medio, nulo}`.
  (verificado en `src/scraper/worker.py:73-112`).

- [x] **Happy Path (persistencia con CHECK constraints):**
  **Dado que** el dict llega a `save_with_outbox`,
  **Cuando** se inserta en `recursos`,
  **Entonces** Postgres valida en SQL:
    - `temporal_class IN ('evento', 'referencia', 'evergreen')`
    - `valor_archivistico IN ('alto', 'medio', 'nulo')`
    - `quarantine_reason IN ('caducidad', 'colision_semantica', 'manual', 'evento_pasado')` (acepta motivo nuevo `evento_pasado` de la migración 0006).
  (verificado en `infra/postgres/migrations/0006_temporal_class_y_strictness.sql:25-40`).

- [x] **Happy Path (índice parcial para queries de auditoría):**
  **Dado que** la mayoría de recursos son `temporal_class='evento'`,
  **Cuando** el cron de auditoría (F-05.1) busca minorías (`referencia`/`evergreen`),
  **Entonces** usa el índice parcial `idx_recursos_temporal_class WHERE temporal_class != 'evento'` (verificado en `infra/postgres/migrations/0006_temporal_class_y_strictness.sql:44-46`).

- [x] **Edge Case (LLM falla / clasificación pasiva):**
  **Dado que** la llamada LLM falla,
  **Cuando** el fallback dict se aplica,
  **Entonces** los defaults seguros son: `category="other"`, `volatility_score="media"`, `estimated_useful_life_days=30`, `temporal_class="evento"`, `valor_archivistico="medio"`, `expiration_date=None`, `event_date=None` (verificado en `src/scraper/worker.py:136-147`).

- [x] **Edge Case (artículo retrospectivo de evento pasado):**
  **Dado que** la URL apunta a `/2024/03/18/feria-x` y el contenido describe un evento ya celebrado,
  **Cuando** el LLM clasifica,
  **Entonces** debería devolver `temporal_class="referencia"` (no "evento") con `event_date="2024-03-18"` y `valor_archivistico` según contenido. Esto **resuelve el gap documentado en migración 0006** (artículos tipo Expojove 2024 / AEMET 2020 que el LLM clasificaba con caducidad sintética futura).

- [x] **Requisito Técnico:**
  - Modelo: `cerebro-lite`, `temperature: 0.1` para clasificación determinística.
  - Strictness por tenant: `usuarios.audit_strictness IN ('estricto','equilibrado','permisivo')` permite ajustar el comportamiento del cron F-05.1 frente a fechas pasadas (default `'equilibrado'`).
  - Backward-compat: rows pre-migración 0006 reciben defaults `temporal_class='evento'`, `valor_archivistico='medio'`, `audit_strictness='equilibrado'`.
  - Trazabilidad: `trace_id` viaja con la metadata hasta la persistencia.
