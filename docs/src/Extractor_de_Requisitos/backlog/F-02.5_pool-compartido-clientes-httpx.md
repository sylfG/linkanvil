**Descripción:**
Como Mantenedor del backend
Quiero **un único `httpx.AsyncClient` por proceso (creado en `connect()` o `lifespan`) que se reutilice para todas las llamadas salientes (LiteLLM, Qdrant, Telegram, Ingestion API)**
Para conservar las conexiones keep-alive y evitar el patrón previo en el que cada llamada abría y cerraba un cliente nuevo, multiplicando sockets en `TIME_WAIT` y degradando la latencia p99 bajo carga.

**Criterios de Aceptación (Checklist):**

- [x] **Happy Path (worker mantiene cliente único):**
  **Dado que** el `scraper-worker` arranca y ejecuta `connect()`,
  **Cuando** se llega a la línea `self.http = httpx.AsyncClient(timeout=30.0)`,
  **Entonces** el worker mantiene una sola instancia para todo su ciclo de vida y la cierra en `close()`; cualquier llamada a `_extract_metadata_with_llm` reusa esa instancia (verificado en `src/scraper/worker.py:162, 171` y firma `_extract_metadata_with_llm(http: httpx.AsyncClient, ...)` en `src/scraper/worker.py:69-70`).

- [x] **Happy Path (firma con cliente parametrizado):**
  **Dado que** `_extract_metadata_with_llm` necesita llamar a LiteLLM,
  **Cuando** se inspecciona su signature,
  **Entonces** el cliente `http: httpx.AsyncClient` viene como primer argumento, no se crea uno nuevo dentro de la función (verificado en `src/scraper/worker.py:69-70, 117`).

- [x] **Happy Path (mismo patrón en embedder-worker y API):**
  **Dado que** el `embedder-worker` y la API (`src/api/main.py`) también consumen LiteLLM/Qdrant,
  **Cuando** arrancan,
  **Entonces** instancian un cliente único (en `connect()` para workers, en `lifespan` para FastAPI) y lo reusan (verificado en `src/data/embedder_worker.py:99` según reporte; cliente global `_http` en `src/api/main.py`).

- [x] **Edge Case (stream largo `/chat`):**
  **Dado que** el endpoint `/chat` mantiene un stream SSE long-lived a LiteLLM,
  **Cuando** se necesita un stream que podría bloquear un slot del pool compartido,
  **Entonces** usa un **cliente dedicado de vida corta** para no atar slots del pool común (decisión consciente para los flujos SSE long-lived, declarada en el backlog original).

- [x] **Requisito Técnico:**
  - Workers exponen `self.http: httpx.AsyncClient` inicializado en `connect()`, cerrado en `close()`.
  - API guarda el cliente en `app.state` o variable global vía `lifespan`.
  - Timeout esperado del backlog: `httpx.Timeout(connect=5, read=120, write=10, pool=10)`. **Drift menor verificado**: el scraper-worker hoy usa `httpx.AsyncClient(timeout=30.0)` (un único timeout global de 30s, sin componentes separados). Es funcional pero menos granular que lo descrito en el AC original.
  - `_extract_metadata_with_llm()` recibe el cliente como parámetro en lugar de crearlo internamente (cumplido).
  - Métrica empírica esperada: con 100 mensajes/min procesados, `ss -tn | grep :4000 | wc -l` debe estabilizarse en ≤10 conexiones a LiteLLM (no crece linealmente con los mensajes procesados).
