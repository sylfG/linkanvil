**Descripción:**
Como Plataforma optimizando coste,
Quiero **compactar el historial antiguo de cada sesión de chat en un `contexto_comprimido` resumido cuando supere N tokens**
Para que las conversaciones largas no enviaran cientos de mensajes en cada llamada al LLM, controlando el coste de tokens sin perder continuidad semántica.

> ⚠️ Estado actual: **PARTIAL** · Falta: la lógica de compactación activa (job/worker/handler que genere el resumen) no existe. La infraestructura de almacenamiento sí.

**Criterios de Aceptación (Checklist):**

- [x] **Infraestructura presente (✅ ya existe):**
  **Dado que** la migración `0001_baseline.sql:106-116` define `sesiones_chat.contexto_comprimido TEXT`,
  **Cuando** el código accede a la sesión,
  **Entonces** los helpers `update_session_context(tenant_id, session_id, new_context)` y `get_session_context(tenant_id, session_id)` en `src/data/db.py:103-139` leen/escriben este campo con respeto a RLS.

- [ ] **Compactación activa (❌ pendiente):**
  **Dado que** una sesión de chat acumula mensajes que superan N tokens (umbral configurable),
  **Cuando** llega un nuevo mensaje al endpoint `POST /chat`,
  **Entonces** un agente/job debe (a) tomar los mensajes más antiguos, (b) llamar al LLM con prompt "resume estos N turnos manteniendo decisiones, hechos y entities", (c) guardar el resultado en `contexto_comprimido` vía `update_session_context`, (d) marcar esos mensajes como compactados (o eliminarlos), (e) en futuras llamadas inyectar `contexto_comprimido` al sysprompt en vez del historial completo.
  > ❌ No implementado: grep negativo de `compactar`/`sliding.*window`/`summarize` en `src/api/main.py`, `src/data/db.py` y `src/data/embedder_worker.py`.

- [ ] **Carga de `contexto_comprimido` en el sysprompt (❌ pendiente):**
  **Dado que** una sesión tiene `contexto_comprimido` no vacío,
  **Cuando** `POST /chat` arma el contexto para LiteLLM,
  **Entonces** debe prependerlo al sysprompt como bloque "## Resumen de conversación previa: …" para que el LLM tenga continuidad sin recibir todo el historial.
  > ❌ Hoy el chat envía hasta los últimos 100 mensajes (cap Pydantic `ChatRequest.messages: max_length=100`) sin sliding window real.

- [ ] **Test de end-to-end (❌ pendiente, actualmente skipped):**
  **Dado que** existe `tests/test_f044_compaction.py`,
  **Cuando** se ejecuta `pytest`,
  **Entonces** el test debería verificar el flujo completo (acumulación → compactación → carga del resumen) — pero hoy está `pytest.skip("Symbols removed from src.ui.chatbot — needs rewrite")` (`tests/test_f044_compaction.py:4`). Hay que reescribirlo contra la API actual.

- [ ] **Requisito Técnico (PENDIENTE):**
  - Umbral configurable vía env var (ej. `CHAT_COMPACT_AFTER_TOKENS=8000`).
  - Tokenización: usar `tiktoken` o equivalente para estimar el número de tokens del historial.
  - Compactación incremental: cada N turnos, no en cada mensaje (coste).
  - Auditable: registrar en `outbox_eventos` cada compactación con el rango de mensajes comprimidos.
  - Reversibilidad: idealmente conservar los mensajes originales (no borrarlos) por si auditoría/export los requiere.

La lógica no se priorizó porque el cap Pydantic (100 mensajes) ya mitiga el peor caso de coste — pero la rentabilidad real del tokenizado en sesiones de 100 mensajes sigue sin optimizar.
- Tests existentes referencian símbolos removidos de `src.ui.chatbot` (módulo Streamlit legacy aún en repo, ver bug en implementation-status.md).
- Relación con F-07.3: el `wiki/hot.md` del exporter sirve `contexto_comprimido` por sesión; mientras F-04.4 no active la compactación, `hot.md` exportará títulos sin contexto compactado real.
