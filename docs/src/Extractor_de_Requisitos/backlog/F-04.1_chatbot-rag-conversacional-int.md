**Descripción:**
Como Usuario consultando mi KB,
Quiero **un chat conversacional en la web que use RAG (top-k chunks de Qdrant) y reciba la respuesta del LLM por streaming SSE**
Para que pueda hacer preguntas en lenguaje natural y ver los tokens aparecer incrementalmente con las fuentes citadas.

**Criterios de Aceptación (Checklist):**

- [x] **Happy Path (streaming RAG):**
  **Dado que** el usuario envía un mensaje vía `POST /chat` (`src/api/main.py:1697`) con `ChatRequest{messages: [...], use_rag: true}` validado por Pydantic,
  **Cuando** el backend (a) busca top-k chunks en `cerebro_chunks` filtrados por `tenant_id`, (b) arma el contexto y lo inyecta en el sysprompt LiteLLM,
  **Entonces** abre `StreamingResponse(_stream(), media_type="text/event-stream")` (`src/api/main.py:1879`) y emite tokens incrementales vía `client.stream(...)` hasta cerrar la conexión; el frontend (`src/frontend/app/(app)/chat/page.tsx`) renderiza con react-markdown.

- [x] **RAG con aislamiento por tenant:**
  **Dado que** el endpoint recibe `req.use_rag = true`,
  **Cuando** ejecuta `points/search` sobre `cerebro_chunks`,
  **Entonces** aplica `filter.must=[{key:"tenant_id", match:{value: <user.tenant_id>}}]` — ningún chunk de otro tenant entra al contexto.

- [x] **Persistencia post-stream (frontend orchestra):**
  **Dado que** el stream del backend cierra,
  **Cuando** el frontend ha acumulado la respuesta completa,
  **Entonces** dispara `POST /chats/{id}/messages` para guardar `user`+`assistant`+`sources` en Postgres (`mensajes_chat`, ver F-04.2 / F-04.6).

- [x] **Edge Case (LiteLLM 5xx o stream cortado):**
  **Dado que** LiteLLM devuelve 5xx o la conexión SSE se interrumpe a medio stream,
  **Cuando** el frontend captura el error,
  **Entonces** muestra mensaje de error inline sin cerrar la sesión del usuario; F-04.6 cubre el `console.warn` ante chunks SSE inválidos.

- [x] **Edge Case (CSRF/auth):**
  **Dado que** un cliente sin cookie de sesión intenta `POST /chat`,
  **Cuando** el dependency `Depends(rate_limit_chat)` y `Depends(verify_csrf)` se ejecutan,
  **Entonces** el request es rechazado con 401/403 antes de tocar la lógica de RAG (`src/api/main.py:1698`).

- [x] **Requisito Técnico:**
  - Endpoint: `POST /chat` con `media_type="text/event-stream"` (no JSON síncrono).
  - Validación: `ChatRequest.messages: min_length=1, max_length=100`; `ChatMessage.content: max_length=32000` (≈ 8k tokens).
  - CSRF: `Depends(verify_csrf)` obligatorio.
  - Rate-limit: `Depends(rate_limit_chat)` por usuario.
  - Frontend: chat page en `src/frontend/app/(app)/chat/page.tsx`, render con react-markdown.

## 📝 Notas de implementación

**Estado**: IMPLEMENTED (verificado 2026-05-19)

**Decisiones tomadas tras el backlog original** (drift documentado):
- **SSE streaming en vez de JSON síncrono**: decisión UX para que el usuario vea tokens aparecer en tiempo real. El backlog original no especificaba transport.
- **RAG sobre `cerebro_chunks`** (no sobre `cerebro_recursos`): los chunks dan mayor precisión en retrieval que el embedding global del recurso.
- **Persistencia delegada al frontend**: el endpoint `/chat` solo streamea; el frontend cierra el ciclo con `POST /chats/{id}/messages`. Esto evita que el backend tenga que persistir partials si el stream se corta.
