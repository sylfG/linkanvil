**Descripción:**
Como Usuario que cambia de dispositivo o pestaña,
Quiero **mis chats persistidos en Postgres y mi sesión de auth en Redis (cookie httpOnly)**
Para que pueda reanudar conversaciones desde cualquier cliente sin volver a hacer login y sin perder historial.

**Criterios de Aceptación (Checklist):**

- [x] **Happy Path (chats persistidos en Postgres):**
  **Dado que** el usuario envía mensajes a un chat,
  **Cuando** el frontend hace `POST /chats/{session_id}/messages` (`src/api/main.py:2024`),
  **Entonces** los mensajes se insertan en `mensajes_chat` (`infra/postgres/migrations/0001_baseline.sql:118-132`) con `sesion_id`, `seq`, `tenant_id`, sujetos a RLS (tenant_isolation policy).

- [x] **CRUD de sesiones de chat:**
  **Dado que** el usuario navega entre conversaciones,
  **Cuando** el frontend llama a la API,
  **Entonces** los endpoints disponibles son (`src/api/main.py:1977-2030`):
  - `POST /chats` → crear sesión (`SessionResponse`)
  - `GET /chats?limit=&offset=` → listar paginado (max `limit=200`)
  - `GET /chats/{session_id}` → obtener sesión
  - `DELETE /chats/{session_id}` → borrar (cascade a mensajes vía FK `ON DELETE CASCADE`)
  - `GET /chats/{session_id}/messages` → mensajes en orden `seq ASC`
  - `POST /chats/{session_id}/messages` → bulk insert

- [x] **Sesión de auth en Redis (cookie + refresh + CSRF):**
  **Dado que** el usuario hace login,
  **Cuando** el backend emite cookies httpOnly,
  **Entonces** establece `cerebro_session` (session ID en Redis), `cerebro_refresh` (refresh token) y `cerebro_csrf` (token CSRF) — la "reanudación sub-ms" viene del lookup Redis del session ID en cada request autenticado.

- [x] **Aislamiento por tenant en mensajes:**
  **Dado que** existe la tabla `mensajes_chat`,
  **Cuando** se aplica la policy `tenant_isolation`,
  **Entonces** solo se devuelven mensajes cuya `sesion_id` pertenece a una `sesiones_chat` del tenant actual (RLS forzada — F-03.4).

- [x] **Edge Case (paginación excesiva):**
  **Dado que** un cliente pide `GET /chats?limit=999999`,
  **Cuando** FastAPI valida los `Query` params,
  **Entonces** devuelve `422 Unprocessable Entity` (cap `Query(le=200)`); equivalente para `/resources` con `Query(le=500)`.

- [x] **Requisito Técnico:**
  - Postgres: tablas `sesiones_chat` y `mensajes_chat` con RLS habilitada y forzada (F-03.4).
  - Índices: `idx_sesiones_tenant` (tenant_id, ultimo_acceso DESC), `idx_mensajes_sesion` (sesion_id, seq ASC).
  - FK: `mensajes_chat.sesion_id → sesiones_chat(id) ON DELETE CASCADE`.
  - Redis: session cookie + refresh token con TTL configurable; cookie httpOnly + SameSite estricto.
  - Aislamiento per-tenant garantizado por RLS, no por filtro WHERE en aplicación.

**Decisiones tomadas tras el backlog original** (drift documentado):
- **La persistencia "ultra rápida" real está en Postgres**, no en Redis. Redis se usa solo para la cookie de sesión de auth (lookup O(1)) y refresh tokens. La promesa de "reanudaciones sub-ms" se cumple por el pool de Postgres + cookie httpOnly, no por almacenar chats en Redis.
- F-04.6 cubre los aspectos concretos de límites Pydantic (max_length de content/messages, caps `Query`).
- "Cross-platform" se refleja en cookie httpOnly + SameSite que funciona en cualquier navegador moderno.
