**Descripción:**
Como Usuario propietario de la KB
Quiero **disparar una auditoría temporal a demanda desde el panel `/profile`,
sin esperar al cron diario**
Para que pueda forzar una revisión del estado (`activo`/`cuarentena`/`expirado`)
de mis recursos tras un cambio importante (ej. import masivo, deduplicación).

**Criterios de Aceptación (Checklist):**

- [x] **Happy Path (auditoría manual):**
  **Dado que** el usuario hace clic en "Auditar ahora" desde `/profile`,
  **Cuando** el frontend llama `POST /resources/audit-now` con header
  `X-CSRF-Token` válido (`src/api/main.py:1456-1475`),
  **Entonces** el backend ejecuta `run_audit_cron()` (la **misma** función
  del cron diario F-05.1) y devuelve
  `{status, trace_id, cuarentenados, expirados}`. Cada invocación produce
  un `trace_id` único correlacionable con los eventos `outbox`.

- [x] **Edge Case (rate-limit por tenant):**
  **Dado que** el usuario hace clic >5 veces en 60s,
  **Cuando** el dependency `rate_limit_audit` evalúa
  `INCR + EXPIRE` en Redis,
  **Entonces** devuelve `HTTP 429` con `Retry-After`. Verificado en
  `src/api/main.py:779,1458` (`rate_limit_audit` aplicado al endpoint).

- [x] **Edge Case (CSRF inválido):**
  **Dado que** el cliente envía la petición sin el header `X-CSRF-Token`
  correspondiente a la cookie `cerebro_csrf`,
  **Cuando** `verify_csrf` valida el doble-submit,
  **Entonces** devuelve `HTTP 403`. El endpoint nunca llega a `run_audit_cron`.

- [x] **Edge Case (idempotencia):**
  **Dado que** el usuario dispara dos auditorías seguidas (separadas por
  >12s para esquivar rate-limit),
  **Cuando** la segunda corre justo después de la primera,
  **Entonces** las dos fases SQL filtran por estado actual y la segunda
  devuelve `{cuarentenados: 0, expirados: 0}` — no hay transiciones espurias.

- [x] **Requisito Técnico:**
  - El endpoint es **idéntico en lógica** al cron diario (F-05.1). No hay
    LLM, no hay agente IA — el adjetivo "Basada en IA" del título original
    es legacy.
  - Autenticación: JWT del usuario en cookie httpOnly. No requiere token
    admin (a diferencia de `POST /admin/audit-cron` que sí lo requiere
    para el cron n8n).
  - Rate-limit: 5 invocaciones por minuto y tenant.
  - Trazabilidad: log estructurado `MANUAL_AUDIT tenant=<id> trace=<uuid> cuarentenados=<n> expirados=<m>`
    (`src/api/main.py:1469-1473`).

**Decisiones tomadas tras el backlog original** (drift documentado):
- El título "Basada en IA" se mantiene por trazabilidad pero **no se cumple
  literalmente**: la auditoría manual es SQL determinística sin LLM. Si en
  el futuro se quisiera un audit "exhaustivo con IA" (revisión semántica
  de cada recurso por el LLM), sería una ficha nueva F-05.4 — no este código.
- A diferencia del cron diario (`POST /admin/audit-cron` con token admin),
  la auditoría manual no requiere token administrativo: la autenticación es
  la del propio usuario y el rate-limit + CSRF protegen contra abuso desde
  la UI.
