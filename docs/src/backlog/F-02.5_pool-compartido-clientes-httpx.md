**Descripción:**
Como Mantenedor del backend
Quiero **un único `httpx.AsyncClient` por proceso (creado en `connect()` o `lifespan`) que se reutilice para todas las llamadas salientes (LiteLLM, Qdrant, Telegram, Ingestion API)**
Para conservar las conexiones keep-alive y evitar el patrón previo en el que cada llamada abría y cerraba un cliente nuevo, multiplicando sockets en `TIME_WAIT` y degradando la latencia p99 bajo carga.

**Criterios de Aceptación (Checklist):**

- [ ] **Happy Path:**
  **Dado que** el `embedder-worker` procesa 100 mensajes/min,
  **Cuando** se mide `ss -tn | grep :4000 | wc -l`,
  **Entonces** el conteo de conexiones a LiteLLM se estabiliza en ≤10 y no crece linealmente con los mensajes procesados.

- [ ] **Edge Case:**
  **Dado que** la llamada `/chat` mantiene un stream largo a LiteLLM,
  **Cuando** se inicia el stream,
  **Entonces** se usa un cliente dedicado y de vida corta para no atar slots del pool compartido (decisión consciente para los flujos SSE long-lived).

- [ ] **Requisito Técnico:**
  Workers exponen `self.http: httpx.AsyncClient` inicializado en `connect()`, cerrado en `close()`. La API guarda el cliente en `app.state` o variable global vía `lifespan` con `httpx.Timeout(connect=5, read=120, write=10, pool=10)`. `_extract_metadata_with_llm()` recibe el cliente como parámetro en lugar de crearlo internamente.
